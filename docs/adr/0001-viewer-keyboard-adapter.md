# The viewer adapts noVNC's keyboard for paste and Num Lock

Covers: `app/web/rfb.js`, `app/web/wall.js`, `app/web/clipboard.js`

noVNC 1.7.0 has no public API for lossless encoding, the first painted frame, paste or lock-state input, so `DesktopRFB` overrides its private methods; retest negotiation, painted pixels, paste order and numpad input when upgrading noVNC. While the person controls a desktop, a paste chord (Ctrl+V, Ctrl+Shift+V, Shift+Insert) first reads their clipboard through the native viewer, hands it to the desktop and only then replays the held keys in their original order. WayVNC and x11vnc use the extended clipboard, where the client only announces new text and sends it when the server asks; keys sent right after the announcement reach the app before the text, so the replay waits for that request, up to one second. The text is sent only when it differs from the last text sent on that stream, so something copied inside the desktop still pastes there. WebKitGTK reports Num Lock as off for every key (checked against WebKitGTK 2.52 on 2026-11-21), and noVNC uses that value to switch the desktop's Num Lock off, which turned numpad digits into navigation keys. The adapter instead reads Num Lock from numpad keys themselves (a digit means on, a navigation key means off) and reports it as unknown for every other key, so noVNC changes the desktop's Num Lock only to match a numpad key.

Considered options: a visible "Send clipboard" button (the previous design) made every paste two steps. Syncing the clipboard whenever it changes would send it to agent desktops the person never pasted into. Sending clipboard text without the announcement handshake skips the server's size limit, which noVNC does not expose.
