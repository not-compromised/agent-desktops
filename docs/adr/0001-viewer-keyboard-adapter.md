# The viewer adapts noVNC's keyboard for paste and Num Lock

Covers: `app/web/rfb.js`, `app/web/wall.js`, `app/web/clipboard.js`

noVNC 1.7.0 has no public API for lossless encoding, the first painted frame, paste or lock-state input, so `DesktopRFB` overrides its private methods; retest negotiation, painted pixels, paste order and numpad input when upgrading noVNC.

While the person controls a desktop, a paste chord (Ctrl+V, Ctrl+Shift+V, Shift+Insert) holds the keys, reads the host clipboard through the native viewer, sends the text, and then replays the held keys in their original order. noVNC's own `clipboardPasteFrom` only announces new text on servers with the extended clipboard and sends it when the server asks, so the app could read the old clipboard before the text arrived. The adapter sends the text unannounced instead, which the extended clipboard permits, so it reaches the server ahead of the keys on the same stream. Text is sent only when it differs from the last text sent on that stream, so something copied inside the desktop still pastes there; a non-text host clipboard clears that memory. Leaving control cancels a pending paste and releases every key the desktop saw pressed, because noVNC switches to view-only before releasing keys and would drop those releases.

WebKitGTK reports Num Lock as off for every key (WebKitGTK 2.52, 2026-11-21), and noVNC used that to switch WayVNC desktops' Num Lock off, turning numpad digits into navigation keys. The adapter reads Num Lock from numpad keys themselves (a digit means on, a navigation key means off) and reports it as unknown for every other key and while Shift is held, which swaps the two. x11vnc takes keysyms rather than scancodes and reports no lock state; with its display's Num Lock off it turns KP_1 into KP_End, so on such servers numpad digits and separators are sent as their plain characters.

Considered options: a visible "Send clipboard" button (the previous design) made every paste two steps. Syncing the clipboard whenever it changes would send it to agent desktops the person never pasted into. Waiting for the server's request after the announcement adds a timeout path and still fails on x11vnc 0.9.16, which never asks. x11vnc stores received text only in CUT_BUFFER0, not in the selections that modern apps read, so paste into Xvfb desktops needs a server-side bridge outside this adapter.
